# ADR-014 — Phase 2 Framework Infrastructure

- **Status:** Accepted
- **Date:** 2026-08-03
- **Phase:** 2 (Framework Infrastructure)

## Context

Every later subsystem (Design Tokens, Render Engine, Component Registry,
Bridges, Animation) needs shared infrastructure: service wiring, events,
WordPress hook management, registries, factories, configuration reads, and
caching. Phase 1 provided a minimal `App` registry and a linear boot
sequence; Phase 2 replaces the registry with a full service container and
adds the cross-cutting services, without touching GeneratePress or vendor
code (ADR-004).

## Decision

1. **Service Container (`Container\Container`):** PSR-11-style container with
   raw values (`set()`), closure bindings (`register()`, `singleton()`), and
   class-string bindings auto-wired "where safe" via constructor reflection.
   Resolution is lazy; singletons are cached; cycles raise
   `CircularDependencyException`; unknown ids raise `NotFoundException`
   (PSR-11). The `App` facade delegates `make()` here while keeping its public
   API stable — existing Phase 1 consumers are unaffected.
2. **Events (`Events\*`):** `EventInterface` + `StoppableEventInterface` +
   `GenericEvent`; `Dispatcher::listen()` / `dispatch()` with ordering (priority
   per listener) and stop-propagation. Framework-internal wiring uses domain
   events (`lumina_core:*`, ADR-006); WordPress actions remain the outward
   surface.
3. **Hooks (`Hooks\*`):** `WpBridge` wraps `add_action`/`add_filter`/`apply_filters`
   behind capability checks (so the framework degrades gracefully outside
   WordPress); `HookManager` deduplicates identical bindings so a listener is
   never registered twice for the same hook/priority.
4. **Registries (`Registry\*`):** `RegistryInterface` + `ArrayRegistry`
   (immutable registration) + `DynamicRegistry` (lazy factory-backed items).
   Used by later phases for components, tokens, and template overrides.
5. **Factory (`Factory\*`):** `FactoryInterface` + `SimpleFactory` — builds an
   arbitrary type id through the container, keeping construction policy in one
   place.
6. **Config Repository (`Config\Repository`):** dot-notation `get()`/`set()`
   over the immutable Phase-1 config array; reads are cheap, writes are
   optional and in-memory only (never persisted).
7. **Cache (`Cache\*`):** `CacheInterface` + namespaced `CacheKey`;
   `ObjectCache` (object-cache abstraction, ADR-010) and `TransientCache`
   (WP Transients) both behind the same interface; `flush()` is honest — it
   only clears keys written through that instance.
8. **Service Providers (`Providers\ServiceProviderInterface`):** `register()`
   (bindings only) then `boot()` (use services) — the approved
   register-then-boot lifecycle. The Kernel boot sequence becomes
   `config → env → flags → logger → errorHandler → container → core services →
providers`, keeping Phase 1 ordering intact and adding framework
   infrastructure as a tail step.
9. **Zero-reflection in production:** reflection-based auto-wiring is limited
   to class-string bindings; explicit closures are the recommended fast path.

## Consequences

- Later phases register cleanly: a phase ships as one or more service
  providers bound in `Config\config.php` (`providers` array) and booted by the
  Kernel — no Kernel changes required per phase.
- The `App` facade stays stable (`make()`/`get()` now resolve through the
  container), so Phase 1 smoke assertions continue to pass unchanged.
- No vendor code, GeneratePress, GP Premium, or WordPress Core modified;
  integrity gate (473/473) still passes.
- Cache and hook services are capability-guarded so the WP-free smoke suite
  can exercise them deterministically in CI.

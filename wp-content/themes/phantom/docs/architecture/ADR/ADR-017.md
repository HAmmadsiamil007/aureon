# ADR-017 — Phase 6 Template System

- **Status:** Accepted
- **Date:** 2026-08-04
- **Phase:** 6 (Template System)

## Context

The Render Engine (Phase 4) renders views and the Component Registry (Phase 5)
names presentational units, but there is no first-class template file
hierarchy, layout composition, partial loading, or dynamic sections. The plan
(§Phase 6) requires: WP template hierarchy integration, an override strategy,
partial loading with fallback, dynamic sections, and child-theme integration —
while GeneratePress remains 100% untouched.

## Decision

1. **Hierarchy resolver** (`Templates\\TemplateResolver`): encodes the
   documented WordPress template hierarchy as data (home/single/page/archive/
   category/tag/author/date/search/404/attachment → ordered candidate names)
   and resolves through the override table — `templates/{override}/{slug}.php`,
   `templates/{slug}.php`, `templates/wp-{slug}.php`, then the parent theme
   directory (GeneratePress) as the final fallback tier, then null. Type
   context (post type, slug, id) builds the most-specific-first prefixes
   (`single-{post_type}-{slug}`, `single-{post_type}`, …).
2. **Partial loader** (`Templates\\PartialLoader`): partials live under
   `templates/partials/`; a missing partial falls back to `index`, and a miss
   with no fallback throws `RenderException` (throws-aware fallback per plan).
   Partial files render through the Phase-4 engine with a ViewModel.
3. **Dynamic sections** (`Templates\\Sections`): plugins/themes register
   renderables (view slugs or callables) against named regions; templates
   render a region so third-party sections emerge in order — no template edits.
4. **Static facade** (`Templates\\View::partial()` / `View::section()`): the
   composition seam templates call; resolves container services lazily, so it
   works identically in WordPress templates and WP-free CLI contexts.
5. **WP boundary** (`Templates\\ThemeTemplatesBridge`): hooks `template_include`
   (capability-guarded) so the resolved child template wins the hierarchy;
   `locate()` is the WP-free test seam. The parent theme is read-only.
6. **Child templates stay minimal and physical**: `templates/single.php`
   composes via `get_header()`/`get_footer()`/`comments_template()` (public GP/
   WP APIs) + `View::partial()`/`View::section()`. Per the blueprint's
   "never shadow/fork GP/Premium files", GP's `header.php`/`footer.php` are NOT
   copied — WordPress falls back to the parent theme automatically.
7. **Frozen-file policy:** the plan lists `Layout::render_sections` and
   `Renderer::render('single')` auto-composition as Phase-6 APIs; rather than
   patching frozen Phase-4 classes, the equivalent capability ships as
   `Sections::render()` + `View::section()` + physical `templates/single.php`
   (which `Renderer::render('single')` already resolves via the base tier).

## Consequences

- `Renderer::render('single')` composes a real page from child templates;
  hierarchy resolution is pure data + path checks (WP-free testable).
- Third-party sections compose into pages without template edits.
- Parent theme stays untouched; the bridge only ever returns child paths or
  defers to WordPress.
- Partial fallback semantics are deterministic (index → throw).
